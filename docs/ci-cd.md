# Автодеплой main

Репозиторий: https://github.com/zoLikeCode/lct_2026_wine
Сайт: https://wine.77-105-169-21.sslip.io/
Запуски деплоя: https://github.com/zoLikeCode/lct_2026_wine/actions/workflows/deploy.yml

`git push origin main` сразу запускает деплой: загрузка именно этого commit SHA →
резервная копия SQLite и кода → переключение релиза. Автотесты, проверки синтаксиса
Python/JavaScript и проверка сборки в CI отключены. Pull request без слияния ничего
не запускает; слияние в main запускает деплой.
Повторить запуск можно в Actions → Deploy wine → Run workflow → main.
Сервер по-прежнему подтверждает запуск приложения для автоматического отката при сбое.
Новые пуши выполняются последовательно; устаревший SHA пропускается, если main уже обновлён.

## Что разворачивается

- `backend/` → `wine_server/` в новом релизе.
- `dist/` → `wine_server/static/mobile/`.
- `wine_curation/*.py` → служебные модули админки.
- `ml/` и `source/` остаются в Git, но не заменяют работающую локальную модель VPS.
  Актуальные точки изменения сайта — **backend и dist**; source — историческая копия.

База, фотографии, модели, секреты и настройки ML хранятся вне релизов:
`/opt/wine/wine_dataset`, `/opt/wine/wine_media`, `/opt/wine/wine_server/models`,
`/etc/wine.env`. Распознавание по-прежнему работает локально на VPS.
Каждый релиз лежит в `/opt/wine/releases/cicd-*`, `/opt/wine/current` указывает на активный.
Сервис перезапускается; на время прогрева модели возможна короткая недоступность.

## Авторизация деплоя

Секретный SSH-ключ или PAT в GitHub не нужен. Deploy job получает короткоживущий
GitHub OIDC JWT. Отдельный непривилегированный сервис на VPS проверяет подпись,
issuer, audience, неизменяемые ID репозитория/владельца, ветку main,
точный файл workflow и SHA. Ни PR, ни другая ветка, ни другой репозиторий не допускаются.
Повтор того же run/attempt не запускает второй деплой. Код сервиса проверки находится
в `ops/oidc_gateway.py`; root-owned копия на VPS не обновляется из обычного пуша.

Worker скачивает публичный архив GitHub по SHA, повторно проверяет main, отклоняет
ссылки, выходы за каталог и слишком большие архивы. Он не запускает shell-скрипты
или установщики из репозитория от root. Приложение запускается пользователем wine.
Секреты из `/etc/wine.env` не передаются Actions и не входят в архив.
Не давайте возможность изменять main/workflow людям, которым нельзя доверить production.
Защиту main / обязательное ревью можно включить отдельно в настройках GitHub.

## Зависимости

CI не устанавливает тестовые зависимости и не скачивает модель.
`requirements-ci.txt` и файлы тестов оставлены для ручного запуска при необходимости.
Сервер использует проверенное `/opt/wine/venv`. Если изменён `requirements.txt`,
автодеплой остановится **до переключения**, чтобы не менять общую среду незаметно.
Для такого релиза администратор должен сначала проверить новую среду, обновить её
и `/var/lib/wine-deploy/runtime-requirements.sha256`, затем повторить workflow.
Для изменения ML нужны отдельная поставка весов и проверка совместимости.

## Откат и наблюдение

Резервные копии: `/opt/wine/backups/cicd-<run_id>.<attempt>/`.
Перед релизом SQLite копируется через online backup API. При неуспешном запуске
worker автоматически возвращает прежний код и перезапускает сервис.
**Живая база не откатывается**, поэтому новые пользовательские действия не теряются.
Изменения схемы должны оставаться совместимыми с предыдущим кодом (расширение, затем миграция).
Остаются пять последних автоматических backup/release; ручные архивы не удаляются.

```bash
ssh root@77.105.169.21
systemctl status wine wine-deploy-gateway wine-deploy-worker
journalctl -u wine-deploy-worker -n 80
curl -fsS https://wine.77-105-169-21.sslip.io/__deploy/version
curl -fsS https://wine.77-105-169-21.sslip.io/api/status
```

Для ручного отката на предыдущий релиз сначала остановите worker (он дожидается
текущей операции), затем замените симлинк current и перезапустите wine. Не восстанавливайте
базу без отдельного решения и копии текущих данных. Предыдущий путь записан в
`backups/cicd-*/release.json`. Для возврата к версии кода через обычный процесс —
`git revert <commit>` и push main; новый коммит сразу разворачивается.

Первоначальная установка инфраструктуры выполняется администратором из `ops/install_server.sh`.
Нужен файл `runtime-requirements.sha256`, полученный `sha256sum requirements.txt` (только хэш).
Порт 8120 доступен только на loopback; внешние обращения идут через HTTPS nginx.
