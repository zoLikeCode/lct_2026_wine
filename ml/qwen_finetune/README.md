# Дообучение Qwen3-VL-Embedding-8B под поиск вина по фото

> **Актуальное состояние:** адаптер v2 из этого документа — в проде, но с индексом из нескольких фото на
> вино и запросом на 2560 токенах: **93.4% top-1 на 379 полевых кадрах**. Цифры ниже — первый замер
> адаптера на 214 кадрах с одним эталоном на вино. Прогоны после него —
> [`STATUS_gpu_runs_20260929.md`](STATUS_gpu_runs_20260929.md), сервис — [`../service/DEPLOY.md`](../service/DEPLOY.md).

LoRA-дообучение мультимодального эмбеддера [Qwen/Qwen3-VL-Embedding-8B](https://huggingface.co/Qwen/Qwen3-VL-Embedding-8B)
на каталожных фото «Своё Вино». Задача та же, что у основного пайплайна: фото бутылки → slug каталога
через поиск ближайшего эталона (один эталон на вино, косинусная близость).

**Итог:** на реальных фото с полки дообученная модель даёт **94.4% top-1** против **88.8%** у текущего
production-бэкбона SigLIP2 so400m-512 на тех же 214 фото (+12 верных ответов). top-5 — 97.2%.

## Результаты

Индекс: 2083 эталона из `catalog_photos` (по одному на вино). Ни одно фото из проверочных наборов
в обучении не участвовало.

| Набор | Что это | SigLIP2 so400m-512 | Qwen без обучения | **Qwen + LoRA** |
|---|---|---|---|---|
| **field** (56) | фото с полки от организаторов, разметка из `outputs/field_labels.csv` | 82.1% / 92.9% | 85.7% / 94.6% | **91.1% / 94.6%** |
| **own** (158) | фото с полки, снятые командой (32 вина, `own_IMG_*`) | 91.1% / 96.8% | 82.9% / 98.1% | **95.6% / 100%** |
| **field + own** (214) | | 88.8% (190) | 83.6% (179) | **94.4% (202)** |
| **val** (310) | отложенные доп. фото каталога 124 вин | — | 83.2% / 99.4% | **90.3% / 99.4%** |

Формат ячеек: top-1 / top-5. Цифры SigLIP получены `retrieval.evaluate_field` на индексе из
`~/Downloads/images` (2082 эталона) — индекс почти тот же, но не побайтово идентичный.

**Оговорки, которые важно учитывать:**

- **field** — всего 56 фото, одно фото ≈ 1.8 пп. 3 из 56 недостижимы для любой модели: вин
  `rozovoe-zoloto` и `oleg` нет в `catalog_photos` (в полном каталоге Никиты эталоны есть). Из
  достижимых верно **51/53 (96.2%)**, все 53 — в top-5.
- **own** — 158 фото, но это 32 вина примерно по 5 снимков, фото одного вина коррелированы.
  Независимых проверок заметно меньше, чем 158.
- **val** — товарная интернет-съёмка из того же источника, что и эталоны. По нему выбирался
  чекпоинт, это не оценка полевого качества.
- Сравнение с SigLIP — по суммарному числу верных, **попарный разбор «исправлено / сломано» по тем
  же фото не делался**. Для строгого вывода по правилу из findings (|исправлено − сломано| ≥
  2·√(исправлено + сломано)) его нужно посчитать.
- Чекпоинт выбран по val, не по field/own — подгонки под тестовые наборы нет.

### Оставшиеся ошибки

Все ошибки на field и own, кроме трёх недостижимых, — путаница соседей по линейке одной
винодельни, верный ответ при этом в top-5:

- own: Бельбек Мускат → Бельбек Пино Нуар (×2), KAFFA Каберне Фран → Каберне Совиньон (×2),
  Мезыбь Мерло → Каберне Совиньон, Уроки французского Мерло → Каберне Совиньон,
  Adagum Odessa Black → Cabernet Sauvignon;
- field: Formula Q Каберне ↔ Саперави, Мерло Литавщук → Мерло;
- на val заметная часть ошибок — дубли самого каталога (`Pinot Noir Reserve` ↔ `Пино Нуар Резерв`,
  `Brut Zero Dosage` ↔ `Brut Zero Dosage`, `Формула Q` ↔ `Formula Q`), которые по фото не различить.

## Как обучали

| Параметр | Значение |
|---|---|
| Базовая модель | `Qwen/Qwen3-VL-Embedding-8B`, bf16, last-token pooling, L2-нормировка (официальный `Qwen3VLEmbedder`) |
| Инструкция | «Represent this photo of a wine bottle to find the exact same wine: producer, wine name, grape variety, sweetness and vintage on the label» — одна для запроса и эталона |
| Разрешение | `max_pixels = 1024·32·32` (~1024 визуальных токена), почти все фото проходят без уменьшения |
| LoRA | r=32, α=32, dropout 0, на `q/k/v/o/gate/up/down_proj` языковой части; визуальный энкодер заморожен. 87.3M обучаемых параметров (1.06%) |
| Оптимизация | AdamW, lr 5e-5, cosine с warmup, micro-batch 16 × accumulation 2, gradient checkpointing |
| Лосс | InfoNCE, τ = 0.05 (см. ниже) |
| Железо | RunPod, 1× A100 SXM 80GB, ~36 с на шаг |
| Лучший чекпоинт | **шаг 40** (~25 минут обучения); дальше качество на плато, прогон остановлен на ~шаге 145 из 158 |

### Данные

Собираются `prepare_manifests.py` из `~/Downloads/catalog_photos` (2083 вина, 4294 фото):

- **эталон** — по одному на вино (`catalog_reference`, иначе `bottle`/`label`) — это и есть индекс;
- **запросы для обучения** — 1681 доп. фото (`_bottle`, `_front_label`) 1959 вин: реальные другие
  ракурсы той же бутылки, с лёгкими аугментациями;
- **имитация фото с полки** — для 40% вин в каждую эпоху из эталона генерируется снимок
  «с полки» (`augment_realistic.py`: цилиндр, поворот на фоне, блик), чтобы в обучении
  участвовали и 1202 вина, у которых нет доп. фото;
- **val** — все доп. фото 15% вин (124 вина, 310 фото) отложены целиком;
- **общие файлы**: 131 файл байт-в-байт одинаков у разных slug (75 групп, 155 вин). Такие фото не
  используются как запросы, а slug одной группы не считаются негативами друг для друга — иначе лосс
  учит противоречие «одна картинка = два вина»;
- **утечка проверена**: ни одно фото field/own не совпадает по md5 ни с одним файлом каталога.

### Лосс и почему он такой

На каждый запрос кандидаты — эталоны всех запросов микро-батча (с градиентом) плюс **трудные
негативы**: 2 случайных из 8 ближайших к целевому вину чужих эталонов (обычно та же линейка той же
винодельни), посчитанные **текущей** моделью без градиента. Таблица соседей обновляется после каждой
промежуточной оценки. Все векторы в лоссе — от одних и тех же весов в одном шаге.

**Первая версия (с банком эмбеддингов) схлопнулась — это стоит знать.** В ней негативами были все
2083 эталона из банка, пересчитываемого раз в 60 шагов, а запрос и его эталон — свежими. Модели
оказалось проще сдвинуть все свежие векторы в одну сторону, чем различать вина: к шагу 60 `loss`
вырос с 0.06 до 1.45 при `acc_vs_bank` = 1.0. Прогон остановлен до первой оценки. Вывод: при
contrastive-обучении с memory bank без momentum-энкодера устаревшие негативы дают модели лазейку;
лечится тем, что все векторы в лоссе считаются текущими весами. В логе v2 за этим следит `ref_cos`
(средняя похожесть разных эталонов батча) — держался 0.31–0.43, схлопывания не было.

### Грабли окружения

- **Потоки CPU.** В контейнере RunPod PyTorch видит 128 потоков хоста при гораздо меньшей квоте:
  препроцессинг картинок шёл 6 с на 16 фото против 0.26 с при 8 потоках, GPU простаивал. Лечится
  `OMP_NUM_THREADS=8 MKL_NUM_THREADS=8` (в `common.py` стоит `torch.set_num_threads(8)`, в воркерах
  аугментации — `cv2.setNumThreads(1)`).
- **Blackwell (RTX 5090) требует PyTorch ≥ 2.7 с CUDA 12.8** — использовался шаблон RunPod PyTorch 2.8.

## Как воспроизвести

```bash
# на Mac: собрать data/ (пути по умолчанию — ~/Downloads/catalog_photos, «Реальные фото», images)
python prepare_manifests.py

# на поде с GPU (A100 80GB), из папки с кодом и data/
bash setup.sh
export OMP_NUM_THREADS=8 MKL_NUM_THREADS=8
python eval.py                                           # точка отсчёта без обучения
python train_v2.py --exp v2                              # обучение, лучший чекпоинт -> runs/v2/best
python eval.py --adapter runs/v2/best --save-index       # метрики + индекс для сервиса
```

## Инференс и ограничения

- Модели нужен **GPU**: 8B в bf16 занимает ~17 ГБ VRAM. На A100 кодирование в батче — 0.22 с на
  каталожное фото и ~0.4 с на полное фото с телефона. **Латентность одиночного запроса на
  целевом железе не измерялась**; на CPU или ноутбуке в SLA 3 с модель не уложится. Решение о
  переходе в прод зависит от того, на каком железе будет работать сервис.
- Адаптер подключается поверх базовой модели: `PeftModel.from_pretrained(model, "runs/v2/best")`
  (см. `eval.py: attach_adapter`), базовые веса перекачивать не нужно.
