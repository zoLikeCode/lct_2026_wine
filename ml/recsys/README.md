# Рекомендации по своей коллекции

Код в приложении — [`backend/recsys.py`](../../backend/recsys.py) (векторы вин, профиль пользователя,
ранжирование), [`backend/taste.py`](../../backend/taste.py) (вкусовые профили) и
[`backend/recsys_service.py`](../../backend/recsys_service.py) (режимы, паспорт, анкета, отклики). Лента и
кандидаты для помощника — `Product.recommendations`. `WINE_RECSYS=legacy` возвращает прежнюю ленту без
деплоя кода.

## Как работает

- **Вино → разреженный вектор** из того, что о нём знает портал: стиль (цвет, сладость, игристое), сорта,
  слова описания вкуса (TF-IDF), блюда, регион, винодельня, крепость и температура подачи.
- **Пользователь → его коллекция:** оценка 5/4 — сильный плюс, 1–2 — минус, бутылка открыта или стоит в
  коллекции — плюс. Избранное и сканы вкус не обучают (это намерение, а не вкус).
- **Счёт вина** — близость к *ближайшему* понравившемуся вину (максимум, не среднее: любителя саперави и
  брюта нельзя усреднить в розовое полусладкое) минус близость к не понравившимся.
- **Холодный старт:** пока сигналов мало, счёт плавно смешивается с популярностью (рейтинги и сканы
  пользователей). На пустой базе — набор стилей в пропорции каталога, у каждого новичка свой.
- **Выдача:** слоты делятся между вкусами пользователя пропорционально уверенности (D'Hondt) плюс доля
  «попробовать новое» рядом со вкусом; MMR против почти одинаковых вин; один slug из группы дублей,
  не больше двух вин одной винодельни. У каждого вина — причина: «Похоже на «X» (ваша оценка 5): сорт
  Саперави, черника, ежевика».
- Жёсткие ограничения запроса (цвет, сладость, блюдо) по-прежнему фильтруют каталог; внутри них
  порядок — по вкусу.

Чистый Python, без numpy: ~30–80 мс на запрос на 2103 винах.

## Офлайн-проверка

Логов пользователей ещё нет, поэтому проверяем основу — похожесть вин — на реальной разметке портала:
у каждого вина скрываем его блюда (34 категории), находим 40 ближайших по похожести **без блока блюд**
и предсказываем блюда по соседям. Соседи из той же группы дублей исключены всегда, в строгом режиме — и
вся винодельня (производители копируют теги по линейке).

```bash
python ml/recsys/eval_pairing.py --strict
```

2035 вин с разметкой:

| Признаки | mAP | P@3 | AUC | mAP (строго) | AUC (строго) |
|---|---:|---:|---:|---:|---:|
| Случайно | 0.172 | 0.084 | 0.50 | 0.172 | 0.50 |
| Самые частые блюда | 0.546 | 0.414 | 0.50 | 0.546 | 0.50 |
| Только стиль | 0.628 | 0.471 | 0.71 | 0.616 | 0.68 |
| + сорт | 0.638 | 0.492 | 0.73 | 0.616 | 0.69 |
| + описание вкуса | 0.658 | 0.504 | 0.77 | 0.627 | 0.71 |
| **Все признаки** | **0.672** | **0.520** | **0.79** | **0.627** | **0.72** |

Что из этого следует: похожесть заметно лучше популярного бейзлайна, а описание вкуса добавляет больше
всего после стиля. Между разными винодельнями прирост от сорта и текста небольшой — разметка блюд
шумная и во многом задаётся производителем, поэтому это проверка представления вина, а не качества
персонализации. Её честно покажут только реальные пользователи: показы и действия стоит логировать.

## Вкусовой профиль вина

[`backend/taste.py`](../../backend/taste.py): у каждого вина пять осей 1–5 (тело, кислотность, танины,
сладость, дуб), до пяти групп ароматов из 13 и поводы. Сейчас профиль строится правилами: сладость из
категории, слова описания («полнотелое», «живая кислотность», «бархатные танины», «черника», «бриошь»),
а чего в тексте нет — из типичного профиля сорта (таблица на 84 сорта каталога).

Сомелье-проход (GigaChat) уточняет профиль по описанию; запускается у себя с ключами из `.env`:

```bash
python ml/recsys/extract_taste_gigachat.py --limit 12   # пробный прогон
python ml/recsys/extract_taste_gigachat.py              # все вина, можно прерывать и продолжать
python ml/recsys/extract_taste_gigachat.py --review 25  # сравнить ответы модели с правилами
python ml/recsys/eval_pairing.py --strict               # проверить, помогает ли
```

Результат — `backend/content/wine_taste.json`, приложение подхватывает его при старте; поле, которое модель
не дала, остаётся из правил.

Честно про пользу: на метрике блюд профиль по правилам ничего не добавляет (стиль и описание уже в векторе),
его вес в похожести небольшой. Он нужен для паспорта вкуса, анкеты новичка (плитки «Насыщенное, с дубом»
сравниваются с винами по осям и ароматам) и подборок под повод. Если сомелье-профиль поднимет метрику —
вес блока стоит увеличить.

## Режимы и API

[`backend/recsys_service.py`](../../backend/recsys_service.py), контракт для фронта —
[`docs/recsys_api.md`](../../docs/recsys_api.md):

- `for_you` — лента; `new` — новый сорт или регион рядом со вкусом; `cellar` — что открыть из своих бутылок
  (с блюдом); `refill` — закончилось: то же вино и похожие;
- подсказки для подборки под повод (праздник → игристое, шашлык → к мясу и не сладкое, подарок → популярное);
- паспорт вкуса (радар по осям, ароматы, стили, сорта, регионы, фраза-итог);
- анкета новичка: цвет, сладость, блюда и вкусовые плитки → виртуальные «понравившиеся вина», которые
  перестают влиять по мере появления своих оценок;
- отклики: «Не то» (лёгкий минус вкусу и скрыть), «Скрыть» на 30 дней, клики; показы пишутся в
  `recsys_events` — из этого потом учатся популярность, совместная встречаемость и ранжирование.

## Дальше

1. Прогнать сомелье-проход и проверить метрикой.
2. Фронт по `docs/recsys_api.md`: анкета, «Не то», «Что открыть сегодня», радар, «Заполнить» в подборке.
3. Когда накопятся отклики: «вместе в коллекциях» (item-to-item) и обучаемое ранжирование на показах.
