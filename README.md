# Сканер российских вин — ML-пайплайн

Поиск карточки вина по фотографии этикетки для платформы «Своё Вино»
(кейс РСХБ.Цифра). Этот репозиторий содержит ML-часть: подготовку каталога,
построение индекса и поиск.

Свод экспериментов и выводов, включая отрицательные результаты, —
[`docs/findings.md`](docs/findings.md). Читать до того, как повторять
гипотезы: часть очевидных идей уже проверена и не работает.

## Текущее состояние

| Что | Значение |
|---|---|
| Покрытие каталога | 2103 из 2103 позиций (100%) |
| **top-1 на честных полевых фото (258: 202 от команды + 56 от организатора)** | **88.4%** |
| top-1 только на 202 полевых фото команды | 89.6% (top-5 95.5%) |
| top-1 только на 56 фото организатора | 83.9% (top-5 98.2%) |
| top-1 на синтетической валидации | 86.0% (не показательна, см. §11.9 findings) |
| top-1 на реальных фото (Archive, 2544 запроса, методологически смещённый) | 79.9% |
| Латентность запроса | медиана 2030 мс, p95 2921 мс (SLA 3000 мс) |
| Пиковая память | ~1.2 ГБ |

Набор команды сократился с 205 до 202 кадров после аудита разметки (§11.33):
пять фотографий лежали не в своей папке, две переразмечены по читаемому на
этикетке названию, три исключены — вино опознано, но в каталоге у него
несколько дублирующих slug. Правки лежат в
`data_prep/field_label_corrections.csv` с обоснованием на каждую.

Все 2103 позиции каталога теперь имеют эталонное фото — прежние 7 непокрытых
(страницы портала каталога возвращали HTTP 404, см. §11.11 в findings) закрыты
фото, присланными вручную пользователем. Это заодно исправило 2 из 9 ошибок
на честном полевом наборе (§11.17): было `top-1 82.1%`, `top-5 94.6%`, вина
`oleg` дважды отсутствовали в индексе (эталоном была афиша фестиваля, не
бутылка) — теперь все ошибки на честном наборе (9 из 56) сводятся к
near-duplicate confusion, ни одной позиции вне индекса не осталось.

Конфигурация: индекс **SigLIP2 so400m 512px** (§11.14 — крупнее модель на
том же разрешении даёт +2.5пп top-1 против base-варианта) по эталонным фото
целиком, top-5 по косинусной близости. **Весь препроцессинг и реранкинг
отключены** (`PREPROCESS=False`, `ORB_WEIGHT=0.0`, `DIFFERENTIATOR_WEIGHT=0.0`):
запрос идёт в эмбеддер целым кадром. Bottle-кроп был включён по результату
на 56 фото (§11.19), но на выросшем до 261 кадра честном наборе знак
развернулся — он теряет точность, рушит top-5 и вдвое дороже по времени
(§11.25).

> **Важно про реранкинг.** ORB давал +8пп на синтетической валидации (запрос —
> искажённая копия того же файла, что в индексе — там ORB узнаёт свои же
> пиксели), но на независимых наборах реальных фото результат обратный: на
> `Archive` (2544 подтверждённых интернет-фото, честный held-out) вес 0.8
> снижает top-1, а перебор весов показывает оптимум ровно в нуле; на наборе
> фото с полки (29 размеченных из 100) ORB активируется лишь на малой доле
> запросов и тоже не даёт прироста. Вывод и разбор — §11.8–11.9, §11.12 в
> findings. Мультиреференсный индекс (§11.12) и generic OCR-реранкинг
> (§11.12) тоже проверены и отклонены. Рабочей частью пайплайна сейчас
> следует считать только embedding-retrieval на so400m; для дальнейшего
> роста нужен принципиально другой метод (VLM-реранкер, обученные матчеры,
> честно провалидированная детекция этикетки, fine-tuning).
>
> **Оговорка по самой валидации** (§11.11 findings): `Archive` и основной
> источник каталожных эталонов (`Downloads/images`) — не независимые
> датасеты, а два снимка одного процесса курирования одной командой из
> одних и тех же интернет-источников. Технической утечки данных нет
> (проверено по содержимому, не только по пути — `retrieval/check_archive_leakage.py`,
> 0 совпадений из 2544), но методологическая близость означает, что 79.9%
> — вероятно, верхняя граница, не оценка по-настоящему полевых условий.
> Честная цифра — на 261 полевом кадре: 56 размеченных фото с полки от
> организаторов плюс 205 снятых командой в магазине (`own_*` в
> `~/Downloads/real_photos`; остальные 421 файла той папки — промо-съёмка
> из тех же источников, что и эталоны, в метрику не входят, §11.25).
> **top-1 86.2%**. Профиль ошибок на двух наборах разный: на 56 фото
> организатора почти все потери — near-duplicate confusion (top-5 98.2%),
> а на 205 фото команды две трети ошибок это полные промахи мимо top-5
> (top-5 94.1%) — там много широких планов полки, где целевая бутылка одна
> из нескольких.

## Установка

```bash
pip install -r requirements.txt
```

Нужен Python 3.12+. Инференс идёт на MPS (Apple Silicon), CUDA или CPU —
устройство выбирается автоматически.

## Подготовка данных

Пути к исходным данным задаются переменными окружения (значения по умолчанию
см. в `data_prep/config.py`):

```bash
export WINE_DATASET_DIR=~/Downloads/Датасет      # дамп организатора
export WINE_HAS_WINE_DIR=~/Downloads/has_wine    # ручная разметка «вино»
export WINE_NO_WINE_DIR=~/Downloads/no_wine      # ручная разметка «не вино»
export WINE_PARSER_IMAGES_DIR=~/Downloads/images # подтверждённые фото по slug (основной источник, см. §11.11)
```

Дальше по порядку — каждый шаг пишет результат в `outputs/`, который не
хранится в git и воспроизводится этими командами:

```bash
# 1. каталог: сопоставление позиций с эталонными фото (~10 секунд)
python -m data_prep.build_catalog

# 2. эмбеддинги каталога (so400m: ~40 минут на 2096 фото, ~1.1с/фото)
python -m retrieval.build_embeddings --backbone siglip2_so400m512

# 3. ORB-дескрипторы каталога — только если включаете --orb-weight != 0,
#    по умолчанию predict.py их не требует (~70 секунд, если нужны)
python -m retrieval.orb_cache
```

Шаг 2 поддерживает `--resume` и пишет чекпоинт каждые ~160 фото: длинные
прогоны на ноутбуке иногда убивает нехватка памяти.

Необязательно, но полезно:

```bash
python -m data_prep.near_duplicates    # отчёт о визуально идентичных позициях
python -m data_prep.shooting_list      # что снимать в магазине, по приоритету
```

## Поиск по фотографии

```bash
python -m retrieval.predict path/to/photo.jpg
```

Печатает top-5 с разложением скора на вклад эмбеддинга и ORB, плюс отрыв
top-1 от top-2. Программный интерфейс — класс `WineFinder` в
`retrieval/predict.py`.

## Замеры

```bash
# точность на равномерной выборке каталога
python -m retrieval.benchmark_catalog --backbone siglip2_so400m512 --sample 400 --aug realistic

# то же с реранкингом и перебором весов
python -m retrieval.benchmark_catalog_rerank --backbone siglip2_so400m512 --sample 400

# латентность и память по этапам запроса
python -m retrieval.measure_latency --backbone siglip2_so400m512 --runs 30
```

Флаг `--aug` выбирает аугментацию: `simple` (плоская перспектива) или
`realistic` (цилиндрическая деформация этикетки, фон полки, наклон, блик).
Вторая ближе к реальным условиям и даёт на 9пп более низкие — то есть более
честные — числа.

Прогоны тяжёлых моделей конкурируют за память: два одновременно уводят машину
в своп и растягивают запрос с 1 до 19 секунд. Запускать по одному.

## Работа с реальными фотографиями

Синтетика не заменяет настоящих снимков — это главное ограничение текущих
оценок.

```bash
# 1. что искать на полке (near-duplicates и непокрытые позиции — в приоритете)
python -m data_prep.shooting_list          # -> outputs/shooting_list.csv

# 2. разметить снятое: фото -> slug, с поиском по каталогу
python -m data_prep.label_field_photos --photos ~/Downloads/field_photos
```

Разметка пишется в формате манифеста организатора плюс истинный slug, так что
по ней можно считать accuracy напрямую. Процесс возобновляемый.

## Структура

```
data_prep/     подготовка каталога: маппинг фото, парсинг slug, near-duplicates,
               инструменты для сбора и разметки реальных фотографий
retrieval/     бэкбоны, индекс, аугментации, поиск, реранкинг, бенчмарки, замеры
docs/          findings.md — выводы всех экспериментов, включая отрицательные
outputs/       результаты прогонов (в git не хранится)
```

## Ограничения

- **Потолок сейчас — 88.4% top-1 на 258 честных полевых кадрах**
  (§11.15/§11.17/§11.33). 79.9% на `Archive` (2544 фото) — методологически
  смещённая, более старая оценка (см. оговорку выше), не использовать как
  основную цифру.
- **Работа с данными окупалась лучше работы с моделью — три раза подряд.**
  Покрытие каталога 93% -> 100% (§11.11), баг эталона `oleg` (§11.15),
  аудит разметки +1.4пп (§11.33). За то же время девять алгоритмических
  методов дали суммарно ноль. Прежде чем строить очередной реранкер, стоит
  проверить данные.
- 18 позиций каталога (0.9%) полностью неразличимы между собой: у одного
  физического вина заведено по 2–5 slug с совпадающими винодельней,
  названием, сортом, цветом, годом, крепостью и сладостью (§11.35). Для
  них верный ответ не определим по фотографии в принципе.
- **Разница в один-два кадра на выборке в полсотни — не результат.**
  §11.19 включил bottle-кроп по разнице 48/56 против 47/56; на выборке 261
  кадра знак развернулся (§11.25), и кроп пришлось отключить. Любое
  будущее решение должно опираться на разницу минимум в 3–4 кадра.
- Реранкинг **поверх целого кадра** закрыт — пять независимых методов
  проверены на честных полевых данных и отклонены: ORB (§11.8–11.9),
  мультиреференсный индекс и generic OCR fuzzy-match (§11.12), точечный
  OCR-дифференциатор near-duplicate пар (§11.18, чистый ноль/минус), кроп
  по **этикетке** (§11.16, снижает top-1 с 81.2% до 68.8%). Причина одна:
  полевые фото часто снимают полку с несколькими бутылками в кадре, и
  сигнал, читающий кадр целиком (OCR, ORB) или обрезающий его слишком
  туго (узкий label-кроп), путает целевую бутылку с соседними или
  выбрасывает полезный контекст.
- Кроп по **бутылке целиком** и OCR-локализация этикетки тоже отклонены
  (§11.24, §11.25) — итого шесть методов. Сейчас в production не работает
  ничего, кроме чистого embedding-retrieval.
- Дальнейший рост, скорее всего, требует либо VLM-реранкера с явной
  инструкцией игнорировать фон (не проверен, статус сети/API на защите
  хакатона не уточнён), либо fine-tuning эмбеддера на hard negatives из
  known near-duplicate пар (`outputs/near_duplicates_report.json`) — но
  у коллеги частичное дообучение SigLIP2 прироста не дало (§11.23).
  Отдельная, не закрытая зацепка: на 205 полевых фото две трети потерь —
  промахи мимо top-5 на широких планах полки, а это другой тип ошибки,
  чем near-duplicate, и чинится он, вероятно, не реранкингом.
